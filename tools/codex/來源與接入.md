## 執行

CI 與本機使用 `.github/驗證計畫.json`，基底必須與 PR／push 一致；全部變更須逐檔對應案例或 Markdown 文件。案例列出契約、直接命令、全部輸入、預估秒數及上限。直接 Vitest 命令須指定測試檔；全套測試不能標成局部。未對應變更直接拒絕，不自動增加測試。

`python -B tools/codex/專案驗證.py --check --evidence-dir <受測樹外的證據目錄>` 只核對計畫；去掉 `--check` 才執行。GitHub CI 以 `--restore-ci` 讀回同倉庫最近的驗證收據；相同案例、內容、驗證器與環境才沿用，PR 編號和提交 SHA 不作測試輸入。Windows 與 Linux 分別判斷，不互相冒充成功。

本輪僅 CI／文件變更，`release=false`；不重建、不重新發布產品。既有單元測試、套件 scripts、型別檢查與離線完整性標準均保留。未來產品變更須更新計畫：明列受影響 Vitest 案例、必要 lint／資料契約檢查，以及依序執行 Archify 核對、TypeScript 編譯、Vite 建置、precache 產生與 verify-dist。五個產物命令必須 `reusePolicy=never`，避免重用收據卻沒有 dist；輸入需包含 runner、相依來源、設定與鎖檔。缺少發布門檻會阻擋，不能用 `release=false` 規避。

正式依賴弱點閘門及非阻擋完整依賴報告保留在真正產品發布流程，不因 CI 文件變更重跑。`securityReview` 必須列 `explicit=true`、`necessity`、`user_quote` 與 `source`；`--audit prod`／`--audit all` 將既有 npm audit 參數交給共用 `verification_gate.py`，使用 `scope=full`、`mode=live` 與 `reuse_policy=never`。不把原腳本存在當作完整掃描授權，也不把套件登錄服務失敗改報通過。

限制：計畫不能自動證明人填寫的影響範圍或傳遞依賴完整；作者須自審。GitHub 工作流程仍保留原 required check 名稱「完整驗證」，但實際範圍是明列局部案例，名稱不是全套成功宣告。Cloudflare 外部建置設定不在此工作流程控制範圍內。
